# Ticket model, validation, and creation semantics

## 1. Ticket object

The service returns and stores a ticket object in the following shape:

```json
{
  "id": "string",
  "title": "string",
  "description": "string",
  "reporter": {
    "name": "string",
    "email": "string | null",
    "vip": false
  },
  "impact": 1,
  "urgency": 1,
  "priority": "P1",
  "state": "new",
  "created_at": "2026-10-14T10:00:00Z",
  "acknowledged_at": null,
  "resolved_at": null,
  "closed_at": null,
  "related_to": null,
  "sla": {
    "ack_due_at": "2026-10-14T10:15:00Z",
    "resolve_due_at": "2026-10-14T14:00:00Z"
  }
}
```

Rules:

- id is opaque, unique, non-empty, generated by the server.
- title is required, length 1..200.
- description is optional and must be at most 4000 characters.
- reporter.name is required, length 1..100.
- reporter.email is optional; when absent or null, it is stored as null.
- reporter.vip is optional; default false.
- impact and urgency are required integers in 1..3.
- priority is computed by the service and never client-controlled.
- related_to is optional and not validated in Lab 1 beyond being carried as a reference.
- created_at, acknowledged_at, resolved_at, closed_at are RFC 3339 instants in UTC.
- sla is always present after creation and contains both due instants.

## 2. Priority matrix

The matrix is the service's starting point under every decision, per R-04 and API.md §3:

| impact \ urgency | 1 | 2 | 3 |
|---|---|---|---|
| 1 | P1 | P2 | P3 |
| 2 | P2 | P3 | P4 |
| 3 | P3 | P4 | P4 |

The precise rules for the selected C3 = matrix are:

- reporter.vip is stored,
- reporter.vip has no effect on the computed priority,
- a VIP ticket remains whatever the matrix dictates,
- priority field in the request body is ignored even if present,
- the service still accepts the input but discards any client-supplied priority.

This specification adopts the decision C3 = matrix, so R-06 is treated as not modifying the priority result; VIP affects visibility, not severity ranking.

## 3. Validation rules

The implementation must reject invalid create requests with 400 or 422 and a JSON error object with a top-level error property.

Required validation:

- title must exist and be 1..200 characters
- description, if present, must be <= 4000 characters
- reporter.name must exist and be 1..100 characters
- impact must be an integer 1..3
- urgency must be an integer 1..3
- unknown fields are ignored
- server-owned fields are ignored if sent by the client
- X-Test-Clock malformed header is rejected with 400 or 422

Invalid examples include:

- missing title
- title length 201
- impact = 5
- urgency = "high"
- unknown field names should not create validation errors
- id in the body is ignored

## 4. Creation semantics

POST /tickets creates a new ticket with:

- state = new,
- created_at = request clock, else current real time,
- all event timestamps null unless already occurred,
- service-computed priority,
- service-computed SLA block,
- optional related_to preserved from request if provided,
- no agent-provided priority accepted

The ticket creation request may contain fields outside the ticket model. Those fields must be ignored.

## 5. Test clock behavior

When the environment variable SVCDESK_TEST_CLOCK is set to 1 or true, each HTTP request may carry X-Test-Clock: <RFC3339 instant>. When present, the value becomes now for that request only.

Rules:

- request timestamp affects created_at and any event timestamps set by the request,
- the clock is per request only,
- the service never compares one request's clock against another's,
- older or later clock values do not invalidate a transition by themselves,
- without the header, now is real UTC time,
- when SVCDESK_TEST_CLOCK is unset or 0, the header is ignored,
- malformed clock value is a validation error.

This is required by R-21 and API.md §8.

## 6. Error format

Errors must be a JSON object with a top-level error field, such as:

```json
{"error": {"code": "validation", "message": "title is required"}}
```

For not found cases:

```json
{"error": {"code": "not_found", "message": "ticket not found"}}
```

The checker requires only the presence of a top-level error object; exact code/message strings are not strictly validated in Lab 1 beyond the expected shape.
